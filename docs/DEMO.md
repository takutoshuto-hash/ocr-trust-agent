# 動画の山場: 台本と撮り方

3 分動画の山場「事故 → エージェントが自分の提案を出し、測り、取り消す」を、毎回同じに再生する手順。
台本は `scripts/demo_story.py` にあり、同じ台本を `tests/test_demo_story.py` が回して結末を固定している。

## 筋（約 90 秒ぶん）

| 場面 | 何が起きるか | 画面 | 一言 |
|---|---|---|---|
| 0 平常運転 | 2 日 × 120 枚を処理。台帳が育ち、郵便番号などは自動で確定 | `/dashboard`（運用） | 「数をさばくほど、人が見る項目が減っていく」 |
| 1 事故 | FAX の劣化で、お届け先の郵便番号の「7」が「1」に見える。住所と合わないので検証で止まり、全部が人に回る | `/review` | 「間違いは 1 件も自動確定していない。人が全部止めた」 |
| 2 その夜 | 振り返りエージェントが修正ログを集計し「郵便番号で 1 を 7 と読み違えやすい」というコツを提案。人が「はい」 | `/briefing` | 「エージェントは提案する。決めるのは人」 |
| 3 翌日 | コツを覚えても直らない。原因は紙の側にある | `/review` | 「読み取りの工夫では、消えたインクは戻らない」 |
| 4 その夜 | エージェントが自分の提案の効果を測る。同じコツの再提案はガバナンスが自動却下。効いていないコツの取り消しを提案。人が「はい」 | `/briefing`、`/proposals?status=rejected` | **「エージェントが自分の提案を取り消す」** |
| 5 復旧 | FAX を修理。読み違いは消え、平常に戻る。全部が監査ログに残っている | `/dashboard`、`/audit` | 「何を提案し、何を取り消したか、後から全部たどれる」 |

## 準備（撮影の前に 1 回）

```bash
cd ~/ocr-trust-agent && source .venv/bin/activate
bash scripts/fetch_fonts.sh          # 手書き風フォント。確認画面に本物らしい紙が出る（無くても動くが、欄に墨を置いただけの紙になる）
```

サーバーは **モック抽出器・メモリ保存** で起動する（`.env` の `GEMINI_API_KEY` は空、`STORE_BACKEND=memory`）。
本番（Cloud Run・Gemini）では事故注入の操作が存在しない（404）ので、この台本は本番では動かない。

```bash
uvicorn app.main:app --port 8000
```

別のターミナルでリハーサル（止まらずに最後まで。承認も台本が行う。約 5 分）:

```bash
cd ~/ocr-trust-agent && source .venv/bin/activate
python scripts/demo_story.py run --auto
```

最後に場面ごとの数字（読み違いの件数、確認の割合、提案の件数）が出る。撮り直すときはサーバーを Control + C で止めて起動し直す（メモリ保存なので白紙に戻る）。

## 本番の撮り方

```bash
python scripts/demo_story.py run          # 場面ごとに止まる。Enter で次へ
```

止まったところで、ブラウザ（http://127.0.0.1:8000）を録画する。

1. **場面 0 のあと**: `/dashboard` の運用表示。「人の確認が要った項目」と「自動で確定できる範囲（項目ごと）」を見せる。
2. **場面 1 のあと**: `/review` に 3 枚残してある。1 枚開き、赤枠の郵便番号（例: 110-0001）を原本どおり（170-0007）に直して確定する。理由欄に「住所と合わない」が出ている。
3. **場面 2 のあと**: `/briefing` を開く。「読み取りのコツを 1 つ覚えさせてよいですか？　お届け先の郵便番号で「1」を「7」と読み違えやすい」に **はい**。根拠に「昨日、人が直した項目が N 件」と出る。
4. **場面 3 のあと**: `/review` をもう一度。まだ郵便番号が並ぶ。
5. **場面 4 のあと**: `/briefing` に「効かなかった読み取りのコツを忘れさせてよいですか？　お届け先の郵便番号のコツは効いていません」。根拠に「覚えさせた時点で人が直した割合は X%、今は Y% で、1 割以上は減っていません」。**はい**。続けて `/proposals?status=rejected` を開き、「（自動却下）…」の行と理由「同じ混同のルールが既に有効。矛盾するルールを積まない」を見せる。
6. **場面 5 のあと**: `/dashboard` と `/audit`。

Enter を押す前に画面を撮り終えること。台本は、人が承認していなければ次に進む前に自分で承認する（撮り直しの取りこぼし防止）。

## 台本の中身（説明に使う事実）

- 事故は `POST /admin/mock/defect` でモック抽出器に入れる系統的な読み違い。1 回目・2 回目の読み取りも欄の再読み取りも同じ癖になる（同じ紙を読んでいるので）。承認済みのコツ（プロンプト注入）では消えない。
- 読み違えた郵便番号は郵便番号↔住所の照合で必ず止まる。だから事故の間、間違いが自動で確定することはない。台帳は修正を受けて即降格する。
- 提案は `_propose_with_rules`（決定的）が「同じ混同が 3 件以上」で出す。承認時に提案時の修正率（**処理した件数あたり**）を基準として保存し、翌晩 `_retractions` が「1 割以上下がっていなければ取り消し」を提案する。分母を「人が見た件数」にすると、翌日に判定が慎重になって人に回る件数が増えただけで率が薄まり、取り消しが出ない（この台本を最初に回したときに見つけた欠陥。`policy.yaml` の `reflection.effect_measure`）。
- 同じ混同（または逆向き）のルールがすでに有効なら、再提案はコードのガバナンスが自動却下し、監査に残す。

## 制約

- 場面はすべて同じ日に起きるので、ダッシュボードの日別グラフは 1 点にまとまる。日ごとの推移は検証結果の表示で見せる。
- 人が確認画面で直す場面は、台本が 3 枚だけ残す（`--leave 3`）。それ以外は台本が正解どおりに確定する。
- 数字（読み違いの件数など）は乱数の種で固定しているが、`--images` で別の帳票を使うと変わる。文言に数字を焼き込まない。
